## Context

The current repository is a deliberately small FastAPI service with one liveness endpoint, a non-root container image, Docker Compose, tests, and CI. It has no persistent application state, media tooling, or storage abstraction. See `proposal.md` for the motivation for adding the first ingestion-to-catalog slice, and the three capability specs for its observable behavior.

The application remains private to the home network and runs on one modest, rootless-Docker Linux server. The design therefore favors a modular monolith and synchronous request handling, but it must establish durable data, migrations, failure cleanup, and operational checks in forms that can grow without a rewrite.

## Goals / Non-Goals

**Goals:**

- Keep one backend image and one FastAPI process while separating API, application, persistence, metadata, and storage concerns at module boundaries.
- Make an import recoverable across validation errors, database errors, duplicate races, and process restarts.
- Make PostgreSQL migrations and both persistent volumes explicit parts of local development, CI, and server operation.
- Keep storage references opaque so a later S3-compatible backend can implement the same narrow interface.
- Test behavior against PostgreSQL and real media parsers rather than using SQLite or mocked parser behavior as integration substitutes.

**Non-Goals:**

- Providing a general distributed transaction between PostgreSQL and the filesystem.
- Optimizing imports as background jobs or scaling search for a large public catalog.
- Defining audio streaming, deletion, playlists, users, permissions, or a frontend-facing authentication model.
- Supporting direct operator placement of files into the media volume; this milestone ingests through the API only.

## Decisions

### 1. Retain a modular monolith with explicit internal boundaries

The backend will remain one Python package, one FastAPI application, and one deployable image. Modules will be grouped around API routes and schemas, import/catalog application services, persistence repositories and models, metadata adapters, and a storage interface. Dependencies point inward: routes coordinate application services; services use repository, metadata, and storage interfaces; infrastructure modules implement those interfaces.

This gives the project realistic separation for tests and later replacement of storage or metadata adapters without creating services, queues, or network boundaries that a single-user server does not need. A fully layered enterprise architecture and separate import worker were considered but rejected because they add deployment and tracing overhead before imports need asynchronous execution.

### 2. Use synchronous SQLAlchemy 2, Psycopg 3, Alembic, and PostgreSQL

Persistence will use SQLAlchemy 2's synchronous session API with Psycopg 3 and explicit Alembic migrations. FastAPI endpoints that perform database, filesystem, or subprocess work will be normal synchronous handlers so FastAPI executes them in its worker thread pool rather than blocking the event loop.

The Compose stack will pin a supported PostgreSQL major image instead of using `latest`. A one-shot `migrate` service, built from the backend image, will run `alembic upgrade head`; the API starts only after PostgreSQL is healthy and migrations complete successfully. CI will run migrations against a real PostgreSQL service. SQLite was rejected because its types, locking, case-insensitive matching, and migration behavior would hide PostgreSQL-specific failures. An async driver was rejected because this workload is dominated by one-at-a-time file and subprocess operations and would add two database programming models without a measured benefit.

The initial `tracks` table will use a UUID primary key and contain the public catalog fields plus a unique SHA-256 digest, opaque audio and optional cover storage keys, cover media type, and timestamps. Storage keys and digests are never serialized by API schemas. A database uniqueness constraint on the digest is the final duplicate invariant.

### 3. Put media behind a small storage interface and use a Docker named volume by default

The application-facing storage contract will cover only the operations this milestone needs: create/write a staging object, atomically promote it to an opaque durable key, open a stored cover, remove an object, and reconcile stale artifacts. The local implementation will maintain separate `staging`, `audio`, and `covers` namespaces beneath one configured root. Keys are relative opaque values generated by the application; callers cannot supply absolute paths or traversal segments.

Compose will mount a named `media_data` volume at the configured storage root. This is still local filesystem storage, persists independently of containers, works cleanly with a non-root process under rootless Docker, and can be backed up with normal Docker volume procedures. Running the API directly may use a git-ignored `./data/media` directory. A host bind mount was considered, but its UID mapping and write-permission setup is unnecessarily fragile for the rootless server; an operator can add an override later if direct host-path access becomes necessary.

The storage interface is intentionally smaller than an S3 API. A later object-store adapter may implement promotion as copy-then-delete while preserving the service contract; the application and database continue to handle opaque keys.

### 4. Execute imports synchronously as a bounded, recoverable workflow

The import service will perform these steps:

1. Stream multipart chunks to a unique staging object while counting bytes and calculating SHA-256. Abort immediately above the configured limit.
2. Use Mutagen and `ffprobe` on the staged file to validate the format and collect embedded and technical metadata.
3. Normalize values and apply deterministic filename fallbacks.
4. Begin a database transaction, take a PostgreSQL transaction-scoped advisory lock derived from the digest, and re-check for an existing digest.
5. Promote the audio and optional cover to newly generated opaque durable keys, insert the track, and commit.
6. Remove staging data in all outcomes. On an ordinary failure after promotion, remove only the newly generated objects after confirming that they are not referenced.

The advisory lock makes identical concurrent imports serialize before promotion, while the unique constraint remains authoritative if an implementation bug or alternate writer bypasses the lock. A duplicate response can therefore identify the already committed public UUID without creating another durable object.

PostgreSQL and a filesystem cannot commit atomically. A process could terminate after promotion but before the database commit. On application startup, a reconciliation pass will run only after database connectivity is available: it removes staging entries and durable objects that are older than a safety grace period and have no database reference. It will never delete media while the database is unavailable. This provides deterministic recovery without introducing an import-state machine or background worker. True distributed transactions were rejected as inappropriate; committing the row before file promotion was also rejected because it can expose a catalog entry whose media does not exist.

The request remains open during processing. The configured 500 MiB default limit and a configurable `ffprobe` timeout bound resource use. If real-world imports later make request latency unacceptable, the application service can be invoked by a job worker without changing the storage, metadata, or repository contracts.

### 5. Inspect content with Mutagen and a timeout-bounded `ffprobe`

Mutagen will read embedded title, artist, album, and the first valid JPEG or PNG cover. Format-specific tag handling will be hidden behind one normalized metadata result. Multi-valued text will be normalized deterministically, whitespace-only values will be treated as missing, and malformed optional cover data will be logged and skipped rather than failing valid audio.

`ffprobe` will be installed through the container image's FFmpeg package and invoked without a shell, with JSON output and a configurable timeout. The adapter will accept only the formats/codecs in the import spec and will translate probe failures into domain errors; command lines, local paths, and raw stderr will not appear in API responses. Trusting extensions or request media types was rejected because both are client-controlled. Mutagen alone was rejected for technical properties because `ffprobe` provides a consistent validation surface across the supported containers.

Tests will create tiny synthetic, non-copyrighted fixtures during the test run. Unit tests may use focused adapter fakes for failure paths, while integration tests exercise real Mutagen and `ffprobe` behavior.

### 6. Expose a narrow versioned catalog API

New product endpoints will live under `/api/v1`; operational `/health` and `/ready` endpoints remain unversioned. Pydantic response models are allow-lists so adding internal model fields cannot accidentally expose a digest or storage key.

List and search will use one repository query plus a matching count query. Search uses an escaped PostgreSQL `ILIKE` substring pattern across title, artist, and album so `%` and `_` in user input are treated as literal characters. Ordering is `created_at DESC, id DESC` for stable pagination. This simple query is adequate for a private catalog; full-text search or a separate search service would be premature.

`PATCH` is limited to title, artist, and album and updates `updated_at`. Cover retrieval resolves the database key through the storage interface and streams the stored JPEG or PNG with its recorded media type. There is deliberately no audio retrieval route in this milestone.

### 7. Separate liveness from readiness and keep diagnostics non-sensitive

`/health` remains a process-only check and never reaches dependencies. `/ready` will perform a bounded database query that proves the migrated `tracks` schema is usable and a create/remove probe in staging storage that proves the application identity can write its configured volume. It will return only named dependency states, never exception strings or configuration values. Detailed failures belong in structured server logs.

Compose health checks can use readiness after startup, while liveness remains useful for distinguishing a live process from unavailable dependencies. A single combined health endpoint was rejected because it makes an infrastructure outage look like a crashed API and would break the established `/health` contract.

### 8. Make configuration, tests, CI, and operations part of the slice

Settings will add the PostgreSQL URL, storage root, maximum upload bytes, `ffprobe` executable, probe timeout, and reconciliation grace period. `.env.example` contains placeholders and usable non-secret defaults; `.env`, media directories, generated databases, and audio files remain ignored. Startup validation will fail clearly for missing required settings but will not print secrets.

The automated suite will include fast unit tests plus PostgreSQL-backed integration/API tests. CI will start PostgreSQL, apply migrations, make `ffprobe` available, run the complete suite, and build the production image. Compose verification will prove the migration job, API readiness, persistence across restart, and the import/catalog path with generated synthetic audio.

Server documentation will include volume discovery, backup and restore, migration execution, update order, readiness checks, and rollback limitations. The production process remains an explicitly invoked Compose deployment; automatic delivery and a self-hosted runner remain separate changes.

## Risks / Trade-offs

- **A synchronous import ties up one request worker during probing.** → Enforce upload and probe limits, keep the service boundary callable outside HTTP, and defer a worker until measured latency justifies it.
- **PostgreSQL and filesystem changes are not a distributed transaction.** → Serialize duplicates, use unique object keys, compensate normal failures, and reconcile only aged unreferenced objects when the database is known available.
- **Malformed media can consume parser resources or exercise native code.** → Stream with a byte limit, invoke `ffprobe` without a shell and with a timeout, run as the existing non-root user, and reject unsupported probe results.
- **A named volume is less directly visible from the host than a bind mount.** → Document inspect, backup, and restore commands and keep the storage abstraction independent of the mount choice.
- **`ILIKE` substring search will eventually scan the catalog.** → Accept this for the expected private collection and introduce indexed text search only after catalog size and query measurements justify it.
- **A migration can make an older image incompatible.** → Back up persistent state before updates, run migrations as an explicit gate, avoid automatic downgrades, and document which releases are rollback-compatible.
- **The unauthenticated import/catalog API can modify data.** → Keep Compose bound to loopback by default and document LAN exposure as an explicit private-network choice; authentication remains required before any public exposure.

## Migration Plan

1. Create a local `.env` from the updated example and choose database credentials without committing it.
2. Build the backend image and start PostgreSQL; verify its health before touching application state.
3. Run the one-shot migration service against the new empty database volume.
4. Start the API with the PostgreSQL and media volumes, then require `/health` and `/ready` to pass.
5. Run an acceptance import using generated synthetic audio and verify detail, listing/search, correction, cover behavior where applicable, and persistence after a Compose restart.
6. On the Linux server, record and test backup procedures for both named volumes before treating imported media as durable.

For rollback, stop the new API and return to the prior image only while the prior release is known to tolerate the new Compose services and schema. Do not automatically run Alembic downgrades or delete volumes. If a destructive schema rollback is ever required, restore the matching database and media backups together; this initial additive migration should normally remain in place during an application rollback.

## Open Questions

- The first alternative storage backend (for example S3-compatible storage on the same server) can be selected later because the opaque-key storage contract does not depend on a specific provider.
- The latency threshold that should move imports to a background worker should be based on observed files and server performance rather than chosen before this synchronous milestone exists.
